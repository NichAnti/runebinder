# Runebinder

A Riftbound companion: track the cards you own, build decks that follow the
official deckbuilding rules, keep a wishlist of what each deck is missing, and
optionally send wishlists to [CardTrader](https://www.cardtrader.com) to buy.

A [Foldkit](https://foldkit.dev) single-page app with Tailwind, deployed to
Cloudflare Workers (Free plan) with [Alchemy](https://alchemy.run). See
[`docs/`](./docs) for the user flows, the system design and the data flows.

## Setup

Requires Nix with flakes. The dev shell provides Bun and Node.js.

```sh
nix develop
bun install
bun alchemy profile edit --add Cloudflare
```

`bun install` also installs the pre-push hook, which runs `bun run check`.
Push from inside `nix develop` so the hook can find `bun`.

Then create `.env` (git-ignored) with:

```sh
INVITE_CODE=<any long random string>   # the code local sign-ups need
CARDTRADER_TOKEN=<your CardTrader API token>   # used once, to seed the card data
```

## Daily work

```sh
bun run dev     # Vite dev server on stage dev_$USER
bun run check   # format check, lint, typecheck, tests
bun run format  # fix formatting
```

## Card data

The card catalogue is never committed. It works like a database with a seed:

- `alchemy.run.ts` declares the R2 bucket `runebinder-data`, shared by every
  stage and by `bun run dev` (it uses the real bucket, not a local stand-in);
  destroying a stage keeps it.
- The first deploy or dev run of each stage runs the `CatalogueSeed` action
  once for the catalogue version in `src/api/catalogue.ts`. It checks whether
  the bucket already has that version. If it does, nothing happens. If not, it
  fetches the cards from the sources (Riot's gallery feed and CardTrader's
  blueprints, with `CARDTRADER_TOKEN`), checks them strictly, and uploads the
  catalogue. So the catalogue is fetched and uploaded once for all stages.
- The browser loads the catalogue from `/api/catalogue/<version>` and keeps it;
  the Backend reads the card types from the bucket to check card ids.

To pick up new cards (a new set), change `CATALOGUE_VERSION` in
`src/api/catalogue.ts`. The next deploy seeds the new version; older versions
stay in the bucket.

Alchemy remembers, per stage, that the seed ran for a version and does not run
it again. If the bucket ever loses the catalogue (for example, it was deleted by
hand), run one deploy or dev run with `--force` (for example
`bun alchemy dev --force`), or bump the version.

The data comes from Riot's gallery feed, which is for development only. Until
the official Riftbound API replaces it, sign-up stays invite only and the app is
not promoted.

## Invites

Sign-up needs the invite code, which the Backend compares with its
`INVITE_CODE` secret. Send people an invite link, which fills in the code:

```
https://<app address>/sign-up?invite=<the code>
```

or give them the code to type in. To stop new sign-ups with an old code,
change the `INVITE_CODE` repository secret and redeploy; existing accounts keep
working.

## Layout

Imports point inward: `domain` ← `api` ← `service` / `worker`.

- `src/main.ts`, `src/update.ts`, `src/view.ts` — the app shell; `src/entry.ts`
  boots the runtime
- `src/page/` — one folder per page, split into `loggedOut/` (home, sign in,
  sign up) and `loggedIn/` (cards, card, decks, deck, wishlists, CardTrader)
  plus the shared state each page reads (collection, decks, wishlist,
  CardTrader connection)
- `src/domain/` — pure Schema types and operations (cards, collection, deck
  rules, deck codes, wishlists)
- `src/ui/` — the design system: tokens in `tokens.css`, one file per component
- `src/service/` — clients used by Commands: the app API, auth, CardTrader,
  the catalogue search index
- `src/api/` — the `HttpApi` contract shared by the browser and the Worker
- `src/worker/` — `gateway.ts` serves the SPA and forwards `/api/*` to the
  private `backend.ts` (Better Auth and the `HttpApi`); Drizzle tables in
  `schema/`, one repository per feature
- `migrations/` — generated by Drizzle; never edit by hand
- `alchemy.run.ts` — the Alchemy stack: the Website and Backend Workers, D1, and the card data bucket

## Deployment

CI (`.github/workflows/deploy.yml`) owns every deploy:

| Event               | Stage    | Result            |
| ------------------- | -------- | ----------------- |
| Push to `main`      | `prod`   | Production deploy |
| PR opened / updated | `pr-<n>` | Preview deploy    |
| PR closed           | `pr-<n>` | Preview destroyed |

Every deploy runs `bun run check` first. The workflow reads the repository
secrets `CLOUDFLARE_API_TOKEN` (which also needs R2 access), `CLOUDFLARE_ACCOUNT_ID`,
`INVITE_CODE` and `CARDTRADER_TOKEN` (used only when a deploy seeds a new
catalogue version).

Do not deploy or destroy `prod` from a local machine.

Workflow: branch, open a PR, check the preview URL in the deploy job output,
merge.
